# Event Catalog

**Document ID:** SPEC-0002

**Version:** 1.0

**Status:** Accepted

**Last Updated:** 2026-07-05

---

# Purpose

This document defines the canonical event vocabulary used throughout Atlas.

While the Event Model Specification defines **what an event is**, this document defines **which events exist**.

Every event published by Atlas must be registered within this catalog.

The Event Catalog serves as:

- The canonical vocabulary for Atlas
- Documentation for developers
- A review mechanism for architectural consistency
- A compatibility contract between services
- A foundation for tooling and validation

---

# Guiding Principles

Every event must:

- Represent a completed fact
- Be immutable
- Have exactly one meaning
- Belong to exactly one domain
- Follow Atlas naming conventions
- Be independently understandable

---

# Naming Convention

Events follow the pattern:

```
<Noun><PastTenseVerb>
```

Examples:

```
DocumentImported
ArtifactCaptured
DeadlineDetected
GoalCompleted
ResearchIndexed
RelationshipUpdated
```

Avoid:

```
ImportDocument
UpdateProject
GenerateSummary
RunOCR
```

These describe commands rather than facts.

---

# Domain Ownership

Every event belongs to exactly one domain.

A domain owns:

- Event definitions
- Payload schema
- Versioning
- Documentation
- Evolution

Other services may consume the event.

Only the owning domain may define it.

# Event Lifecycle Categories

Every event belongs to one of four lifecycle categories.

```
Created

Updated

Completed

Archived
```

Additional lifecycle events should be introduced sparingly.

---

# Reserved Event Suffixes

The following suffixes are reserved and should be used consistently.

| Suffix | Meaning |
|---------|----------|
| Created | New object exists |
| Imported | Existing external object entered Atlas |
| Captured | Information recorded from user input |
| Updated | Metadata or state changed |
| Completed | Work finished |
| Archived | No longer active |
| Deleted | Removed from active storage |
| Detected | Atlas inferred something |
| Generated | Atlas produced new derived information |
| Linked | Relationships established |
| Merged | Multiple objects combined |
| Failed | Operation did not complete |
| Started | Long-running activity began |
| Stopped | Long-running activity ended |
| Resolved | Problem corrected |

---

# Event Governance

Adding a new event requires:

1. Architectural review
2. Domain ownership assignment
3. Payload definition
4. Version assignment
5. Documentation update
6. Compatibility review

Events should not be created ad hoc within implementation code.

---

# Deprecation Policy

Events should rarely be removed.

When necessary:

- Mark as deprecated
- Introduce replacement
- Continue supporting historical replay
- Never rewrite historical event logs

---

# Tooling Expectations

Future Atlas tooling should be capable of generating:

- Event documentation
- Payload schemas
- Type definitions
- Validation rules
- Replay compatibility reports
- Service dependency graphs

directly from this catalog.

The Event Catalog should become the single source of truth for event definitions.
